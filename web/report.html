2What is built

Three agents, three dispute types, every exchange on the record; four additional safeguards on top.

Core

  • Three agents. Two advocate agents pull evidence through logged tools, write a brief and an append-only rebuttal; a tool-less judge answers only the questions the policy engine left open. Each is a separate role contract. Court feed (replay page) · Court UI
  • Structured ruling and plain-language notices. Structured ruling with outcome, amount, model confidence, reasoning, cited facts and clauses, rejected claims, and a plain-language notice to each party. Ruling card · Reproducibility receipt
  • Evidence from every source. Every case file carries a 5-second GPS trace, the quoted route, chat, driver statement, fare breakdown, LTA traffic bands and incidents, weather and both profiles; code turns them into a numbered fact table. Fact table (expand on the replay page)
  • Three dispute types. Route deviation and no-show / cancellation fee, plus safety as a third (escalation-only) type — 6 hand-built demo cases and 49 benchmark cases cover all three. Demo cases · Benchmark
  • Every exchange on the record. Every tool call, brief, rebuttal point, judge question and verifier check is an event streamed live (server-sent events) and replayed in the court feed with timestamps. Run live on the replay page · Court UI

Additional safeguards

  • Precedent store. Rulings are indexed; a new case retrieves similar past cases by fact values and the judge sees them as context (never as evidence). A ruling that contradicts strong precedents raises a warning.
  • Bad-faith signals. Code-computed signals — arrival tap far from the pickup, waiting claim unsupported by GPS, jam claim unsupported by traffic data, repeat offender — enter the fact table as citable facts. C-0004 facts
  • SLA routing and review queue. Each ruling is routed: auto-resolve, 24-hour review, or urgent safety (2 h). Anything the certificate cannot clear, any account action and any high signal goes to a human.
  • Human feedback loop. A reviewer's override is recorded, becomes a human-labelled precedent that outranks automatic ones, and feeds an override-rate statistic per dispute type.

3Data and method

49 synthetic benchmark trips on real OneMap road geometry, each built around one trap a careless system would fall into, plus 6 hand-built demo cases.

Caveats

  • Synthetic data: the 49 benchmark cases are generated scenarios on real OneMap routes, not Ryde tickets, written by the developers.
  • Reference answers are derived from the policy engine plus scenario labels. 'Correct' therefore means 'agrees with the written policy', not 'agrees with a human ops team'.
  • One model (deepseek-chat) for all four arms; results may differ with other models.
  • 49 cases is a small set and the scenarios are related; percentages move by about 2 points per case, and each case moves a percentage by about two points.
  • The court costs roughly 7× the input tokens and 4× the latency of a single call — still seconds, against 24–72 h of manual handling.

How the reference answers were made, and what the numbers can and cannot say

  • Each benchmark scenario is written around one trap (a timestamp just before or after a rule boundary, a decoy incident, an unnamed stop, a fake arrival tap, a threat keyword). The reference answer is produced by running the policy engine on the scenario's own labels and checking it against the trap the scenario was written for.
  • The court's certificate gate and the reference answers share that policy engine. A shared bug would therefore be invisible to this benchmark: the result is a policy-conformance test, not evidence that the written policy or its implementation is what a human ops team would decide.
  • Raw LLM receives the case JSON with the GPS trace thinned to one point every 30 s (native sampling 5 s) to fit the context window; everything else is verbatim. It is never given fact ids, so it cannot cite them.
  • All four systems use the same model with the same temperature settings; the court was additionally run with identities swapped and a second time on every case.

4How it works

Raw evidence — GPS trace, chat, fare lines, timestamps, both profiles, the OneMap route and LTA traffic — first passes through pure code: fact tools produce a numbered fact table and the policy engine runs every clause as a predicate. Two advocates then pull facts through logged tools, write briefs and rebuttals, and a tool-less judge answers only the questions the code left open. A verifier checks every citation and compares the ruling with the certificate: only a matching ruling is cleared for automatic execution; everything else goes to the review queue, and every outcome carries a reproducibility receipt.
