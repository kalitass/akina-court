2What is built

Three agents, three dispute types, every exchange on the record; four additional safeguards on top.

Core

  • Three agents. Two advocate agents pull evidence through logged tools, write a brief and an append-only rebuttal; a tool-less judge answers only the questions the policy engine left open. Each is a separate role contract. Court feed (replay page) · Court UI
  • Structured ruling and plain-language notices. Structured ruling with outcome, amount, model confidence, reasoning, cited facts and clauses, rejected claims, and a plain-language notice to each party. Ruling card · Reproducibility receipt
  • Evidence from every source. Every synthetic case file carries a 5-second GPS trace (the organisers' sample is sampled every 3 minutes), the quoted route, chat, driver statement, fare breakdown, LTA traffic bands and incidents, weather and both profiles; code turns them into a numbered fact table. Fact table
  • Three dispute types. Route deviation and no-show / cancellation fee, plus safety as a third (escalation-only) type — 6 hand-built demo cases and 65 benchmark cases cover all three. Demo cases · Benchmark
  • Every exchange on the record. Every tool call, brief, rebuttal point, judge question and verifier check is an event streamed live (server-sent events) and replayed in the court feed with timestamps. Replay page (Run live needs a local copy with a DeepSeek key) · Court UI

Additional safeguards

  • Precedent store. Rulings are indexed; a new case retrieves similar past cases by fact values and the judge sees them as context (never as evidence). A ruling that contradicts strong precedents raises a warning.
  • Bad-faith signals. Code-computed signals — arrival tap far from the pickup, waiting claim unsupported by GPS, jam claim unsupported by traffic data, repeat offender — enter the fact table as citable facts. C-0004 facts
  • SLA routing and review queue. Each ruling is routed: auto-resolve, 24-hour review, or urgent safety (2 h). Anything the certificate cannot clear, any account action and any high signal goes to a human.
  • Human feedback loop. A reviewer's override is recorded, becomes a human-labelled precedent that outranks automatic ones, and feeds an override-rate statistic per dispute type.

3Key features

The AI argues; only verified policy executes.

  1. The policy runs before the model. Ryde's dispute rules are compiled into executable predicates: on every case, code first decides which of the 17 sourced clauses apply, which fail and which need a reading, and the model speaks only inside that remaining space. A ruling rests on the written policy, not on the model's memory of it, which removes the room for an invented rule at the source.
  2. Every ruling is verified by code, and the evidence chain cannot be tampered with. The facts are computed by code from the GPS trace, the chat, the fare, traffic and weather records: numbered, identical on every run; the advocates and the judge may cite only those numbers and the clause ids. Before anything executes, code checks the ruling item by item: every cited id exists, the outcome is one the policy allows, the amount equals the policy formula to the cent, a consent message precedes the detour it excuses. Each ruling carries a receipt with four fingerprints (case file, policy, code, model), so any change anywhere invalidates it. 6 deliberate tampers of the AI's output (a cited fact that does not exist, a fact never read, an invented clause, a changed amount, a flipped finding, an account flag hidden in free text) and a prompt injection planted in the chat were all caught.
  3. The reasoning is fully transparent and the standard is documented. Every tool call, brief, rebuttal, ruling, check and notice is a timestamped event, streamed live and replayable step by step on the map; every citation opens the fact or the clause it points to. Across the benchmark the court made 1242 citations, 0 of them invalid.
  4. Adversarial agents beat the same model alone. Same model, same 65 cases. The raw case file handed straight to the model: 34 of 65 right or handed to a person, 31 wrong decisions executed. The judge with the code check but no advocates: 58 of 65, 7 wrong decisions executed. The full court (code facts, two advocates, judge, code check): 65 of 65, 0 wrong decisions executed. The advocates add what a single judge lacks: each side states the policy ground of every open question, a point both sides agree on binds the judge, and a judge may only rule as one of the argued grounds does. On the 12 held-out cases, written after the prompts were frozen and never used for tuning, the court decided 11 of 12 right with 0 wrong decisions executed.

Responsible AI

  • Safety complaints and account actions are never automated; a threat in the chat stops the court and the case goes to a person.
  • Insufficient evidence is a formal finding: a GPS hole, a missing record or an agreement the record cannot tie to the road sends the case to a person, with what is missing named.
  • The notices to rider and driver are plain language, and their amounts are checked by code against the final ruling.

4Data and method

65 synthetic benchmark trips on real OneMap road geometry, each built around one trap a careless system would fall into, plus 6 hand-built demo cases.

Caveats

  • Synthetic data: the 65 benchmark cases are generated scenarios on real OneMap routes, not Ryde tickets, written by the developers.
  • Reference answers are derived from the policy engine plus scenario labels. 'Correct' therefore means 'agrees with the written policy', not 'agrees with a human ops team'.
  • One model (deepseek-chat) for all four arms; results may differ with other models.
  • 65 cases is a small set and the scenarios are related; one case moves a percentage by about two points.
  • The court costs roughly 7× the input tokens and 4× the latency of a single call — still seconds, against 24–72 h of manual handling.
  • The benchmark set was extended from 49 to 65 cases on 2026-10-11, after the first four-system results had been seen; the added cases were written from the policy and the record like the others, every one that passed the generator's gates was kept, but they are not held-out. The held-out set is scored separately.

How the reference answers were made, and what the numbers can and cannot say

  • Each benchmark scenario is written around one trap (a timestamp just before or after a rule boundary, a decoy incident, an unnamed stop, a fake arrival tap, an ordinary pickup message that contains a threat hint word). The reference answer is produced by running the policy engine on the scenario's own labels — what the rider meant, whether a message is a threat — and checking it against the trap the scenario was written for.
  • The court's certificate gate and the reference answers share that policy engine. A shared bug would therefore be invisible to this benchmark: the result is a policy-conformance test, not evidence that the written policy or its implementation is what a human ops team would decide.
  • Raw LLM receives the case JSON with the GPS trace thinned to one point every 30 s (native sampling 5 s) to fit the context window; everything else is verbatim. It is never given fact ids, so it cannot cite them.
  • All four systems use the same model with the same temperature settings.
